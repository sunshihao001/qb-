# HER_DOC Project Constitution

Status: `CONSTITUTION_ACTIVE`
Scope: `/root/sikk-gmgn/system/her_doc/`
Canonical purpose: turn documents, research, legacy assets, and operator goals into evidence-backed system objects, not prose summaries.

## 1. Identity

HER_DOC is an **evidence-level document-to-system control project**.

HER_DOC is not:

- a generic summary tool;
- a report generator;
- a simple directory scanner;
- a direct code fixer for trading logic;
- a runtime/trading enabler;
- a replacement for K00-K08, P01-P10, R00, P09, or P10.

HER_DOC is:

- a document function extraction protocol;
- a knowledge/system assetization preparation layer;
- a gap-to-queue router;
- an evidence requirement generator;
- a safe runtime-binding review preparer;
- a guard against treating text as implementation.

## 2. Authority Hierarchy

When HER_DOC is invoked, authority order is:

1. Explicit user scope and safety boundary.
2. This constitution.
3. `HER_DOC_EXECUTION_PROTOCOL.md`.
4. HER_DOC schemas in this directory.
5. Repository rules: `/root/sikk-gmgn/AGENTS.md` and directory constitution docs.
6. Existing HER document-function-system assets under `/root/sikk-gmgn/system/her_document_function_system/`.
7. Legacy scripts, data, reports, and GPT research as read-only evidence/candidates.

If an older report pattern conflicts with this constitution, this constitution wins.

## 3. Core Principle

AI understanding is not system state. A claim becomes HER_DOC state only when represented as a file-backed object with status, evidence, and next action.

Required conversion chain:

```text
natural language / document / research / old asset
  -> document_passport
  -> functional_object_registry
  -> system_mapping_matrix
  -> evidence_requirement_matrix
  -> gap / queue / blocker / handoff
  -> validator result
```

## 4. Data Pollution Boundaries

HER_DOC must keep these separated:

- explanation vs implementation;
- candidate research vs accepted rule;
- legacy asset vs current runtime asset;
- path inference vs file-read evidence;
- dry-run evidence vs live-runtime approval;
- queue created vs work completed.

Any ambiguity must downgrade status instead of filling gaps by inference.

## 5. Required Default State

For non-trivial work, default successful state is:

`EVIDENCE_READY_WITH_GAPS`

Stronger states require explicit evidence:

- `ACCEPTED_FOR_DOWNSTREAM` requires downstream handoff/acceptance packet.
- `RUNTIME_BINDING_VERIFIED` requires safe-mode runner/import/dry-run proof.
- `FULL_FLOW_ACCEPTED` requires protocol completion plus validator pass and downstream evidence.

## 6. Forbidden Shortcuts

HER_DOC must not:

- use chat context as source of truth;
- mark a report as execution evidence;
- mark a queue item as completed work;
- mark a plan as implementation;
- call path existence runtime binding;
- call dry-run live readiness;
- rewrite legacy assets without an absorption record;
- enable trading, signing, broadcasting, auto-order, or deployment.

## 7. Project-Level Success

HER_DOC project success means the control system exists and can be invoked consistently:

- constitution exists;
- execution protocol exists;
- schemas exist;
- overclaim and safety guards exist;
- completion status taxonomy exists;
- future scan prompt exists;
- Hermes skill exists;
- validation can distinguish `PASS`, `PASS_WITH_GAPS`, `BLOCKED`, and `REJECTED`.
