# SIKK Stable Trader OS HER 任务书生成标准

## 1. 标准定位

本文件定义 SIKK Stable Trader OS 专用 HER 任务书的生成规范。

它不是普通需求说明。
它不是聊天式提示词。
它不是实施建议。

它是所有阶段任务进入系统前的统一任务书标准。

目标是让任何阶段任务都必须被写成：
- 可执行
- 可校验
- 可审计
- 可阻断
- 可降级
- 可验收

凡不符合本标准的任务书，视为 *未完成建模*，不得进入代码落地。

---

## 2. 任务书定义

HER 任务书是阶段任务的系统化执行契约。它必须同时描述：
- 为什么做
- 由谁做
- 读什么
- 写什么
- 按什么顺序做
- 何时阻断
- 何时降级
- 何时验收
- 如何交接给下一阶段

任务书不是自然语言摘要，而是可直接进入系统编排的执行蓝图。

---

## 3. 必须包含的 22 项

任何 SIKK Stable Trader OS 任务书，必须按以下 22 项组织，且顺序不得随意打乱：

1. 任务身份
2. 系统总目标
3. 当前阶段定位
4. 本次任务边界
5. 禁止事项
6. 必须读取的总控文件
7. 系统接入与认知更新要求
8. 必须创建的目录
9. 必须创建的文件
10. 执行顺序
11. 模块职责
12. 输入输出合约
13. schema 要求
14. handoff 要求
15. 状态码规则
16. 硬否决规则
17. missing 处理规则
18. 测试要求
19. 验收命令
20. 审计报告
21. 最终状态
22. 下一步规则

任意一项缺失，任务书不合格。

---

## 4. 任务身份

任务身份必须唯一、可路由、可追踪。

必须至少包含：
- 任务名称
- 任务 ID 或阶段 ID
- 目标系统名称
- 所属阶段
- 版本或批次标识

示例要求：
- `phase_01_data_fact_controller`
- `phase_02_wallet_structure_controller`
- `phase_06_strategy_gate_controller`

禁止只写“优化一下”“继续完善”“修复问题”这类模糊标题。

---

## 5. 系统总目标

任务书必须显式引用 SIKK Stable Trader OS 的总系统目标。

系统总目标写法必须满足：
- 说明系统不是单点功能
- 说明系统服务于阶段化结构化闭环
- 说明系统只接受证据链、状态码、交接、审计
- 说明系统禁止直接跳过阶段边界

不得只写成“让功能更好”或“完成任务”。

---

## 6. 当前阶段定位

必须明确任务属于哪一个阶段。

至少要写清：
- 阶段编号
- 阶段名称
- 阶段目标
- 阶段上下游关系
- 是否允许进入下一阶段

若当前任务不属于任何已定义阶段，则必须显式标记：
- `STAGE_INCOMPLETE`
- 或 `PHASE_UNDEFINED`

不得把阶段定位写成“见情况处理”。

---

## 7. 本次任务边界

必须明确本次任务做什么、不做什么。

边界必须包含：
- 允许改动的范围
- 不允许改动的范围
- 是否允许新增文件
- 是否允许改已有文件
- 是否允许受控替换旧实现
- 是否允许只做文档不做代码

如果任务只是文档标准化，就必须写明 *不执行代码任务*。
如果任务是代码落地，就必须写明 *必须产生可运行代码*。

---

## 8. 禁止事项

任务书必须列出本次任务的禁止事项。

至少包括：
- 禁止新增阶段
- 禁止跳过总控文件
- 禁止用空模板冒充完成
- 禁止省略 contract / schema / handoff / audit
- 禁止没有验收标准
- 禁止没有最终状态
- 禁止绕过硬否决
- 禁止用 `0`、空字符串、伪值冒充 missing
- 禁止把建议项写成必须项
- 禁止把普通自然语言当作执行规范

禁止事项必须是可审计的规则，而不是情绪化提醒。

---

## 9. 必须读取的总控文件

任务书必须列出本次任务执行前必须读取的总控文件。

至少应包含：
- 总控 Skill
- 阶段控制器文件
- contract index
- schema index
- handoff flow
- hard negative rules
- directory constitution
- 总控审计结果
- 相关专业基线文件

写法必须明确到文件路径或稳定文件名。

如果某些文件尚未存在，必须写入：
- `missing`
- 并说明是缺失、待创建还是待核验

不得用“相关文档若干”一笔带过。

---

## 10. 系统接入与认知更新要求

任务书必须说明本次任务如何进入系统，而不是只产出静态文档。

至少必须写清：

- 被哪个 control-plane 文件引用
- runtime state 如何消费
- `next_allowed_task` 如何解析
- gap register 如何同步
- audit report 写到哪里
- handoff packet 是否生成或读取
- 哪些规则可作为 durable cognition candidate
- 哪些 gap/missing 不得进入长期认知

如果任务只生成文档但未接入控制面，必须标记：

```text
DOCUMENT_READY_ONLY
SYSTEM_INTEGRATION_PENDING
```

不得声明：

```text
SYSTEM_READY
FULL_SYSTEM_BUNDLE_READY
```

---

## 11. 必须创建的目录

任务书必须列出本次任务必须创建或确认存在的目录。

目录必须是具体路径，且符合系统目录宪法。

必须说明：
- 哪些目录是主写入目录
- 哪些目录是共享交接目录
- 哪些目录是审计目录
- 哪些目录只是只读补查目录

若任务不需要创建新目录，也必须明确写出：
- `无新增目录`
- 并说明原因

不得隐式创建目录。

---

## 12. 必须创建的文件

任务书必须列出本次任务应创建、修改或验证的文件。

每个文件必须注明：
- 路径
- 类型
- 角色
- 是否必需
- 是否可降级

常见类型包括：
- contract
- schema
- runtime module
- test
- audit report
- handoff packet
- gap register

不得只列文件名，不列路径。

---

## 13. 执行顺序

任务书必须给出可执行顺序。

顺序必须满足：
1. 先读总控
2. 再判阶段
3. 再看 contract
4. 再看 schema
5. 再看 handoff
6. 再实施
7. 再测试
8. 再审计
9. 再交接
10. 再决定最终状态

如果任务是多步骤实现，每一步必须可独立验证。

不得把“整体做完再说”作为顺序描述。

---

## 14. 模块职责

任务书必须说明本次任务涉及的模块职责。

必须至少区分：
- 总控层
- 阶段控制器
- Atomic Skill / 子模块
- runtime 模块
- validator
- test
- audit
- handoff writer

如果任务只涉及文档，也必须说明哪些职责不启动。

禁止把控制层、执行层、审计层混成一层。

---

## 15. 输入输出合约

任务书必须明确输入输出合约。

至少包含：
- 输入文件
- 输入字段
- 关键上下文
- 输出文件
- 输出字段
- 下游读取文件

如果输入缺失，必须写出：
- 缺什么
- 缺失后如何降级
- 是否阻断

如果输出是结构化文件，必须说明输出格式：
- JSON
- CSV
- MD
- JSONL

不得只写“根据输入生成输出”。

---

## 16. schema 要求

任务书必须写明 schema 要求。

至少包括：
- 哪些文件需要 schema
- schema 路径
- 必需字段
- 可选字段
- missing 字段语义
- 额外字段是否允许
- 版本管理方式

如果任务不涉及 schema，也必须写明：
- `schema not applicable`
- 以及理由

不得让结构化输出没有 schema 约束。

---

## 17. handoff 要求

任务书必须规定 handoff。

至少包括：
- handoff 文件路径
- 下游阶段
- 下游需要读取哪些文件
- handoff 是否共享副本
- handoff 是否可阻断
- handoff 是否可降级
- handoff 里必须包含哪些状态字段

handoff 必须可被下游直接读取，不能只作为注释存在。

不得省略 handoff packet。

---

## 18. 状态码规则

任务书必须列出本任务使用的状态码，并说明其语义。

至少要区分：
- READY
- READY_WITH_GAPS
- REJECTED

以及本任务阶段的具体状态码。

状态码必须满足：
- 可枚举
- 可继承
- 可阻断
- 可审计
- 不依赖自然语言猜测

不得使用未注册状态码。

---

## 19. 硬否决规则

任务书必须写出硬否决规则。

硬否决必须高于所有正向解释。

至少包括：
- 上游输入缺失到阻断阈值
- contract 严重不全
- schema 不可用
- handoff 不可用
- 出现非法执行字段
- 出现越权阶段跳转
- 出现违反目录宪法的写入

硬否决必须写清：
- 触发条件
- 阻断后动作
- 是否允许降级
- 是否允许继续下一阶段

不得让下游覆盖上游硬否决。

---

## 20. missing 处理规则

任务书必须规定 missing 的处理方式。

必须明确：
- 何时记为 missing
- 何时降级
- 何时阻断
- 何时允许继续
- 何时必须写入 gap register

必须禁止以下做法：
- 用 `0` 冒充 missing
- 用空字符串冒充 missing
- 用默认值冒充 missing
- 用推测值冒充 missing

missing 必须进入：
- audit
- handoff
- 需要时进入 gap register

---

## 21. 测试要求

任务书必须给出测试要求。

至少包括：
- 单元测试
- 合约测试
- schema 测试
- handoff 测试
- 关键降级路径测试
- 硬否决测试
- 必要时的集成测试

测试要求必须写清：
- 测试目标
- 通过条件
- 失败条件
- 运行命令

不得允许“后面再测”。

---

## 22. 验收命令

任务书必须写出验收命令。

至少包括：
- 运行测试命令
- 运行验证命令
- 运行 mock / sample / smoke 命令
- 必要时的审计命令

验收命令必须是可复制执行的命令形式。

不得只写“执行测试”而不写命令。

---

## 23. 审计报告

任务书必须说明本次任务会生成哪些审计报告。

至少应包含：
- 主审计报告
- 输出验证报告
- handoff 验证报告
- missing gap 报告
- 必要时的执行轨迹报告

审计报告必须回答：
- 做了什么
- 缺了什么
- 阻断了什么
- 降级了什么
- 下一步怎么接

---

## 24. 最终状态

任务书必须有最终状态定义。

最终状态至少三态：
- `READY`
- `READY_WITH_GAPS`
- `REJECTED`

必要时可加阶段专用状态，但必须映射到三态之一。

最终状态必须说明：
- 是否允许进入下阶段
- 是否允许代码落地
- 是否必须先补 gap
- 是否必须停止

没有最终状态的任务书视为无效。

---

## 25. 下一步规则

任务书必须写明下一步如何处理。

至少包括：
- 若 `READY`，下一步做什么
- 若 `READY_WITH_GAPS`，先补什么再做什么
- 若 `REJECTED`，先修什么再重跑什么

下一步规则必须可直接变成后续任务书输入。

不得让任务在完成后“自然消失”。

---

## 26. 标准输出形态

所有符合本标准的任务书，推荐输出为 Markdown。

但其内容必须是结构化执行规范，而不是散文式说明。

建议采用如下块级结构：
- 标题
- 任务信息
- 约束
- 依赖
- 文件清单
- 执行顺序
- 合约
- 测试
- 验收
- 审计
- 状态
- 下一步

---

## 27. 质量门槛

一个任务书只有同时满足以下条件，才算符合本标准：
- 结构完整
- 阶段可路由
- 输入输出明确
- contract / schema / handoff / audit 齐全
- 有测试要求
- 有验收命令
- 有审计报告
- 有最终状态
- 有下一步规则

若不满足，必须标记为：
- `HER_TASKBOOK_INCOMPLETE`

---

## 28. 适用范围

本标准适用于 SIKK Stable Trader OS 的所有阶段任务，包括但不限于：
- 数据事实层
- 结构地址层
- 筹码控制层
- 场景识别层
- 结构位置层
- 策略过滤层
- 执行风控层
- 复盘学习层
- 系统升级层

本标准不新增阶段，只规范已有阶段任务的写法。

---

## 29. 使用方式

以后任何阶段任务，只要进入 HER 体系，就必须先被写成符合本标准的任务书，再进入实施。

换句话说：

> 先任务书，后执行。
> 先合约，后代码。
> 先审计，后升级。


## 30. 标准结论

本标准的完成定义是：

- 能让任务路由到正确阶段
- 能让输入输出显式化
- 能让缺失项显式降级或阻断
- 能让审计和 handoff 成为强制项
- 能让后续 phase_01_data_fact 代码落地任务书自动继承同一结构

最终状态定义为：

```text
READY
READY_WITH_GAPS
REJECTED
```

以上三态是所有符合本标准任务书的唯一最终结果通道。
