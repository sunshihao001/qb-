# 文档处理工作体系重建

## 从“解释性文档”升级为“HER 可理解、可调度、可执行、可验收的功能化知识系统”

---

# 0. 先给结论

你现在的判断是对的。

当前上传到 HER 的文档如果只是：

```text
解释概念
说明方法
描述系统
总结认知
列出原则
```

HER 很容易把它当作普通背景资料读取，而不是当作：

```text
可执行目标
阶段控制器
任务树
输入合约
输出合约
字段模型
验收标准
工具绑定要求
状态回写规则
```

所以现在要重建的不是“文档整理方法”，而是：

```text
Knowledge-to-Function 文档处理工作体系
```

它的目标不是让 AI “看懂一篇文章”，而是让 AI 把文档转成：

```text
系统知识对象
阶段任务对象
功能候选对象
数据字段对象
合约对象
验收对象
HER 执行任务包
```

# 1. 新认知：文档不应该直接给 HER 执行

你现在的原始流程大概是：

```text
GPT 里研究文档
  ↓
总结成说明性文档
  ↓
上传 HER
  ↓
希望 HER 理解并执行
```

问题在于：

```text
说明性文档 ≠ 可执行任务包
解释性知识 ≠ 阶段控制器
方法论总结 ≠ 可调度单元
```

专业版应该变成：

```text
原始资料
  ↓
K00 知识摄取
  ↓
知识对象化
  ↓
功能候选化
  ↓
阶段映射
  ↓
Phase Controller 候选任务化
  ↓
HER 执行任务包
  ↓
验收 / trace / handoff / backlog
```

核心转变是：

> **文档不是给 HER “阅读”的。**  
> **文档是被处理成 HER 可以运行的系统对象。**

---

# 2. 文档处理体系的总架构

建议新建一个独立体系：

```text
Knowledge Processing Program：知识处理计划
```

不要混入 P01-P10，也不要混入 I01-I05。

它位于系统最上游：

```text
原始资料 / GPT 研究结果 / 外部文章 / 方法论文档
  ↓
K00-K08 Knowledge Processing Program
  ↓
system_methodology_blueprint.md
  ↓
P00 / Bootstrap / Governance / Domain / Data / Control / Trace / Acceptance / Handoff
  ↓
P01-P10 Phase Controller
  ↓
I01-I05 Integration Program
  ↓
Continuous Paper-only Operation
```

# 4. 每个阶段负责什么

## K00：知识摄取与任务化总控

### 核心定位

K00 不只是“接收文档”。

它应该是：

```text
文档进入系统后的第一道控制器
```

负责判断：

```text
这份文档是什么类型？
它应该被当作知识资料、方法论、系统设计、任务需求、字段模型，还是执行指令？
它是否能直接进入 HER？
是否需要先转成 Phase Controller 候选？
是否需要先抽取字段 / 合约 / 验收标准？
```

### 必须输出

```text
k00_intake_manifest.yaml
k00_document_type_classification.yaml
k00_processing_route_decision.yaml
k00_taskization_requirement.yaml
k00_to_k01_handoff_packet.yaml
```

## K02：语义切块与概念抽取

### 目标

把长文档拆成 AI 可稳定处理的结构。

不是普通摘要，而是抽取：

```text
核心概念
方法论原则
操作步骤
判断条件
输入数据
输出数据
限制条件
隐含假设
系统缺口
可转化功能
```

### 输出

```text
semantic_chunk_index.yaml
concept_registry.yaml
method_principle_registry.yaml
assumption_registry.yaml
constraint_registry.yaml
unknown_gap_registry.yaml
```

### 核心区别

普通摘要问：

```text
这篇文章讲了什么？
```

K02 问：

```text
这篇文章里哪些内容能变成系统对象？
哪些是判断条件？
哪些是输入字段？
哪些是输出字段？
哪些是验收标准？
哪些只是解释，不能执行？
```

# 5. 文档类型分类体系

HER 处理文档前，必须先分类。

```yaml
document_type_classification:
  EXPLANATORY_DOC:
    description: 解释性文档
    action: 不能直接执行，必须功能化

  METHODOLOGY_DOC:
    description: 方法论文档
    action: 抽取原则、流程、判断模型、验收标准

  SYSTEM_DESIGN_DOC:
    description: 系统设计文档
    action: 映射到控制器、合约、schema、目录、状态机

  PHASE_CONTROLLER_DOC:
    description: 阶段控制器文档
    action: 检查是否具备身份、职责、输入、输出、trace、acceptance、handoff

  TASK_INSTRUCTION_DOC:
    description: 任务指令文档
    action: 编译成 HER task package

  RUNTIME_REPORT:
    description: 运行报告
    action: 转入 P09 review / I05 closed loop

  UPGRADE_PROPOSAL:
    description: 升级建议文档
    action: 进入 P10 controlled upgrade review

  FIELD_MODEL_DOC:
    description: 字段 / 数据模型文档
    action: 进入 schema / contract candidate
```

# 6. 解释性文档转功能文档的标准公式

任何文档都要按这个公式处理：

```text
解释内容
  ↓
核心机制
  ↓
可执行动作
  ↓
输入对象
  ↓
输出对象
  ↓
判断条件
  ↓
限制条件
  ↓
验收标准
  ↓
系统映射
  ↓
HER 任务包
```

例如：

```text
“AI 要先理解文档再执行”
```

转化为：

```yaml
control_rule:
  name: document_understanding_before_execution
  rule_type: PROCESS_CONTROL
  required_before_execution:
    - document_type_classification
    - objective_extraction
    - system_mapping
    - taskization_requirement
  forbidden:
    - direct_execution_without_classification
    - treating_methodology_as_plain_summary
  acceptance:
    - processing_route_declared
    - output_objects_declared
    - handoff_target_declared
```

# 9. 文档处理 Hard Negative Rules

```yaml
knowledge_processing_hard_negative_rules:
  - rule_id: KP_BLOCK_001
    name: 未分类文档直接执行
    result: BLOCK
    reason: 文档必须先经过 document_type_classification

  - rule_id: KP_BLOCK_002
    name: 解释性文档直接当任务执行
    result: BLOCK
    reason: 解释性文档必须先功能化

  - rule_id: KP_BLOCK_003
    name: 方法论未映射系统阶段
    result: BLOCK_OR_READY_WITH_GAPS
    reason: 方法论必须映射到 controller / schema / contract / acceptance

  - rule_id: KP_BLOCK_004
    name: 无输入输出对象
    result: BLOCK
    reason: 没有 I/O 对象，HER 无法执行

  - rule_id: KP_BLOCK_005
    name: 无验收标准
    result: BLOCK
    reason: 无 acceptance，无法判断完成

  - rule_id: KP_BLOCK_006
    name: 无 handoff
    result: BLOCK
    reason: 无法交给下游阶段

  - rule_id: KP_BLOCK_007
    name: 文档直接修改生产系统
    result: BLOCK
    reason: 文档只能生成候选，不能直接改生产系统

  - rule_id: KP_BLOCK_008
    name: 单篇文档直接生成全局规则
    result: BLOCK
    reason: 单文档只能生成 candidate，需 P10/Governance 审查

  - rule_id: KP_BLOCK_009
    name: 忽略不确定性
    result: BLOCK_OR_GAP
    reason: 必须标记假设、缺口、未知项

  - rule_id: KP_BLOCK_010
    name: 无 trace
    result: BLOCK
    reason: 每个知识对象必须追踪来源
```

# 10. HER 读取文档的新指令方式

以后不要只发：

```text
理解这份文档
总结这份文档
根据这份文档完善系统
```

应该发：

```text
请按 Knowledge Processing Program 处理这份文档：

1. 先生成 document_passport
2. 判断 document_type
3. 按 20% overlap 进行 semantic chunking
4. 抽取 concept / method / constraint / assumption / gap
5. 抽取 functional_object_candidate
6. 判断映射到 K00 / P00 / Governance / Data / P01-P10 / I01-I05 / CPO 哪一层
7. 生成 controller_candidate / schema_candidate / contract_candidate / acceptance_candidate
8. 编译 HER task package
9. 输出 acceptance_result
10. 输出 handoff_packet

禁止：
- 不要只总结
- 不要直接修改生产系统
- 不要把解释性内容当可执行规则
- 不要无验收标准输出任务
- 不要无 trace 输出结论
```

# 本次认知升级点

1. **文档不是直接给 HER 阅读的，而是要被处理成功能化知识对象。**
    
2. **解释性文档必须经过 K00-K08，才能进入系统建设。**
    
3. **HER 真正需要的不是总结，而是 task package、schema、contract、acceptance、handoff。**
    
4. **K00 的核心不是摄取文档，而是判断文档该如何被任务化。**
    
5. **文档处理体系应该独立于 P01-P10 和 I01-I05，作为上游知识加工层。**
    
6. **任何文档中的规则、字段、控制器都不能直接生效，只能先成为 candidate。**
    
7. **真正专业的文档处理结果必须包含 trace、gap、acceptance、handoff。**
    
8. **下一步应该先建立 `Knowledge Processing Program`，再把已有文档重新处理一遍。**
